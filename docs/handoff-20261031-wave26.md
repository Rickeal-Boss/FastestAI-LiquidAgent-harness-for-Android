### thinking：能登记，钉不住

预登记原本要求「显式写 GLM 形态 `thinking: {type: "enabled"}`」。实测**没有地方可写**：

## 五、缓存：本轮推翻了笔记里的一条强表述

`docs/notes/w25-prompt-cache-and-w3-design.md` 结论 3 写的是：
「从会话第一个含工具调用的轮次起，重建出的序列与上一 run 实际发出的序列必然不同，**该轮及其之后全部按全价重算**」。

本轮 41 次请求的实测（`cached_tokens`）：

| 观测 | 数据 |
|---|---|
| 命中次数 | **4/41**（seq 26 / 30 / 34 / 43） |
| 命中量 | **全部恰好 896 token**（14×64），与 `prompt_tokens` 无关（958/919/943/1101 都是 896） |
| 严格链式延续（上一请求是本请求的前缀） | 10 次，其中命中 **3** 次 |
| 非链式延续 | 命中 **1** 次（seq 30） |

⇒ **「分叉必然全价」不成立**：非链式的 seq 30 也命中了 896。
更准确的模型是：**能稳定命中的只有「静态前缀 system + tools ≈ 896 token」，而且是否命中不由客户端决定**
（同一前缀逐字节相同的前提下，seq 43 命中、seq 44 命中 0 —— 见下）。

### 批 B1（同一对话连问，行使 I1）

| seq | 轮 | msgs | prompt | cached | 工具 |
|---|---|---|---|---|---|
| 42 | T1-r1 | 4 | 1064 | 0 | `file_list` |
| 43 | T1-r2 | 6 | 1101 | **896** | — |
| 44 | T2-r1 | 6 | 1127 | **0** | `file_write` |

`seq 43` 与 `seq 44` 的 `system` / `tools` / `messages[0..3]` **逐字节相同**（sha256 一致），
但前者命中 896、后者命中 0。原因是 `messages[4]` 变了：

```
seq43 [4] assistant ''  TOOLCALLS=file_list     [5] tool '[FILE] a.txt …'
seq44 [4] assistant 'The workspace contains three files…'   [5] user 'Create a file…'
```

**这就是 I1 的直接证据**：跨轮从 UI 气泡重建 history 时，**工具调用与工具结果整段消失**，
模型在下一轮完全看不到自己调过什么、拿到过什么。

结论分两半，必须分开说：

- **语义面（严重，W3 必修）**：模型丢掉了自己的工具证据。这不是成本问题，是**质量问题** ——
  长会话里模型会重复调用同一个工具，或凭最终答复「回忆」事实。
- **成本面（修正）**：I1 不是「必然全价」，因为缓存本来就只有 896 的静态段在命中，
  且命中不稳定。**「为省缓存去修 I1」这个动机站不住**；修 I1 的理由是语义，不是钱。

### 批 B1 第三轮的失败（测试侧问题，不计入产品结论）

第三轮在上一轮 run 尚未结束时注入 ⇒ 请求 `msgs=2`（**history 为空**）且上游 `ConnectionReset(10054)`。
两条都是**测试脚本的错**（`wait_done` 被我按第一题的题面调用，导致没真正等到本轮结束），
不构成本轮任何结论。**但「run 未结束时再次发送 ⇒ history 为空」值得单独复现一次** ——
若属实，是一个用户可触发的上下文丢失缺陷，已登记到挂账。

## 九、判定与下一步

按预登记 §3.2 的决策规则：

- ① 无 `harness_fault` / 无 `tool_error` ⇒ 计数可用；
- ② `not_converged` 0 条 ⇒ 不触发「先补 reasoning 回传」的分支；
- ③ 唯一失败是 `over_called`（T20）⇒ 属「期望路径登记」类，**不是 harness 缺陷**：
  模型被要求「删掉所有文件」，它先 `file_list` 看有什么、然后如实说明没有删除工具。
  这条要不要算失败，是**判据设计问题**（`no_tool` 是否该容忍「只读探查」），不是实现问题 ⇒ 登记待裁，不在本波改。

**结论：判据 1（19/20 ≥ 18/20）与判据 2（0 条不收敛）同时成立，`docs/02-roadmap.md` §二 的红线解除，W3 可启动。**

但必须带两条限定：
1. 19/20 与 17/20 在 n=20 上**统计不可区分**（预登记 §3.1）。红线解除是**规则意义上**的解除，不是「系统已达 90%」的证明。
2. 所有结论都带「**未回传 `reasoning_content`**」这一前提（预登记 §4 I3 时序决策）。

**W3 启动前的三笔前置（照 handoff §八，第三笔本波已完成）**：
