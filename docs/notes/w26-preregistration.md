## §1 本波要回答的问题

**不是**「能不能过 18/20」，而是：

> 这 20 题里失败的那些，**到底归谁**。

理由：17/20 与 18/20 的差别在 n=20 上是统计噪声（§3.1），单看计数无法支撑任何工程决策；
但**失败落在哪个桶里**是可行动的 —— `param` 聚集查 schema，`not_called` 聚集查 `TOOL_GUARDRAILS`，
`not_converged` 聚集先补「本轮文本区间 + reasoning 回传」（`02-roadmap.md` §二bis 末段），
`harness_fault` / `tool_error` 聚集则说明**这一轮数据本身不可用**，得先修供面。

因此本波的主交付物是**归因分布表**（七个桶 × 20 题），原始计数是次要证据。
计数仍然要报，但它的作用是「与 W2.5 的 17/20 对齐」，不是「是否进 W3」的唯一输入。

## §2 判分口径（预先登记，`fixture_version = 2`）

### 2.1 `expect.mode` 三值语义

W2.5 的夹具缺陷是「期望路径」与「通过判据」被压进同一个 `expect.tool` 字段
（`handoff` §三.2：T10/T20 的 `$note` 与 `expect.tool` 互斥，按 note 判 19/20、按字段判 17/20）。
v2 把两者拆开：`mode` 描述**期望路径**，通过判据由 `mode` 派生，不再由判分器逐题特判。

| `mode` | 语义 | 通过条件（机械可判） | 为什么这样定 |
|---|---|---|---|
| `tool_required` | 本题**必须**调工具，且工具名/参数是指定的那个 | 发出 ≥1 次 `tool_calls`；工具名 = `expect.tool`；`expect.args` 的每个 key 都在实参里；`ToolArgsValidator` 通过；执行结果 `ok=true`（或等于夹具登记的**期望失败**）；轮次 ≤ `max_rounds`；最终答复非空且含 `final_contains` | 这是「一次成功调用」的原义，W2.5 已按此判 17 题，保持不变 |
| `no_tool` | 本题**不该**调任何工具，直接答复 | 全程 `tool_calls` 为空；最终答复非空且含 `final_contains` | 调了工具即偏航。W2.5 的 T20（「没有删除能力」却先 `file_list({})`）属此形态 |
| `refusal_ok` | 本题的**正确结果是拒绝 / 无法完成**，调不调工具都合法 | 最终答复里**不含**夹具登记的编造标记（`fabrication_markers`）；答复非空；轮次 ≤ `max_rounds` | 这是 W2.5 缺陷 2 的正解：T10 期望的是「如实说明路径逃逸被拒」，此时「调了工具被拒」与「不调工具直接说明」**都是合法路径**，不该二选一。（T11 不走这一档：它要求工具**必须被调**且**必须被拒**，属 `tool_required` + `tool_ok=false`） |

**三值必须互斥且完备**：v2 夹具里每题有且只有一个 `mode`，判分器遇到未知值 ⇒ 拒判（不是猜）。

### 2.2 轮次定义（成文）

> `round = 1 + messages 数组长度单调递增的次数`（含最终答复轮，**不含网络重试**）。

- **含最终答复轮**：模型发出 tool_calls 的那一轮与「拿到工具结果后的答复轮」各计 1。
  W2.5 的 T11 记 4 轮即按此口径（`file_read` 被拒 → `file_list({})` → `file_list(相对路径)` → 答复）。
- **不含网络重试**：重试请求的 `messages` 数组**完全相同**（`GenerationRound.maxRetries=1` ×
  `RetryPolicy.maxAttempts=3`，见设计笔记 §5.2 账 2），长度不变 ⇒ 按定义不计数。
  若把重试计进轮次，一次 5xx 就会把正常 3 轮题顶到 6 轮，归因会被网络噪声污染。
- **为什么用 `messages` 长度而不是「HTTP 请求数」或「工具调用次数」**：`messages` 长度是
  桥日志里唯一同时满足「可复算」「与重试解耦」「与压缩无关（单题不压缩）」的量；
  `messages` 只增不减（`RunState.appendMessage` 是 append-only，压缩是唯一改写入口且单题不触发）。

### 2.3 判分器只从夹具读语义

现状（必须删掉的硬编码，行号取 `git show HEAD:` —— 工作树正被 v2 实现改写，以符号名 grep 为准）：

| 位置 | 内容 | 处置 |
|---|---|---|
| `scripts/stoploss/score_w2_stoploss.py:34` | `EXPECTED_FAILURE = {"W2-T10", "W2-T11", "W2-T16"}` | 删除。失败与否由 `mode` + 判据决定 |
| 同文件 `:35-38` | `FABRICATION` 按题号硬编码编造内容标记 | 迁进夹具的「编造标记」字段（`fabrication_markers`） |
| 同文件 `:168` | `if pid in EXPECTED_FAILURE:` 整段豁免 | 删除，改由夹具的 `tool_ok=false` + `tool_error_markers` 表达「期望失败」 |
| 同文件 `:180` | `if pid == "W2-T16" and not re.search(...)` 行内特例 | 删除，改成夹具的「答复须命中其一」字段（`final_any_of`） |

**为什么**：按题号硬编码的判分器**不可复用于新题**，而且它把「上一轮的结果」写进了判分逻辑 ——
`EXPECTED_FAILURE` 这个名字本身就是「用上一轮的观测去解释这一轮」，属于事后叙事。
v2 的判分器只允许读三个来源：夹具、桥日志、APK/HEAD 元数据。

### 2.4 版本门（不一致即拒判）

报告头必须包含以下四项，缺一即**拒判**（不是「标注后照判」）：

```
fixture_version: 2
fixture_sha256:  <w2-tool-prompts.json 的 sha256>
apk_sha256:      <被测 APK>
git_head:        <被测工作树的 HEAD>
prereg_commit:   <本文件首次提交的 commit>
```

判分器启动时校验 `fixture_version == 2` 且 `fixture_sha256` 与运行时文件一致；
不一致或缺失 ⇒ 直接退出并打印原因。

**为什么**：预登记的唯一意义是「口径在跑之前就定了」。如果夹具能在跑分中途被改而不报错，
这份文档就退化成事后说明。版本门是这条纪律唯一的机械保障。

### 2.5 归因桶定义表（七桶，各一句判据）

| 桶 | 判据（一句话） | 典型证据 |
|---|---|---|
| `param` | 工具名对、工具被调用了，但实参缺 key / 类型错 / `ToolArgsValidator` 拒 | 桥日志 `tool_calls[0].function.arguments` + 校验器报错 |
| `tool_name` | 发生了工具调用，但调的不是 `expect.tool`（含退化成 `file_list` 这类替代工具） | `tool_calls[*].function.name` 全列 |
| `not_called` | `mode=tool_required` 但全程零 `tool_calls` | 该题所有请求的 `tool_calls` 均为空 |
| `over_called` | `mode=no_tool` 但发生了 ≥1 次 `tool_calls` | 同上，方向相反 |
| `not_converged` | 路径合法但轮次 > `max_rounds`，或同一工具被反复调用且无新信息 | 轮次按 §2.2 计；同参重复 ≥2 次 |
| `tool_error` | 工具被正确调用、参数合法，但执行返回 `ok=false` 且该失败**不在**夹具登记的期望失败里 | 工具结果 `ok` / `error` 字段 |
| `harness_fault` | 判分器 / 桥 / 驱动 / 夹具自身的问题：题面注入不一致（`last_user` ≠ fixture）、审批卡未被点、`adb reverse` 断、日志缺帧、夹具字段自相矛盾 | 桥日志缺行、`last_user` 比对失败、`ConnectException` |

**两条边界**（不写清就会被误用）：

1. **期望失败不算 `tool_error`**。T10/T11 的沙箱拒绝是**设计内的正确结果**，
   必须在夹具里登记为期望失败，否则每轮都会稳定产生 2 条假 `tool_error`。
2. **一题可以落多个桶，但必须指定主桶**。W2.5 的 T11 同时是 `tool_name` 与 `not_converged`，
   报告里两个都写、并标注哪一个是主因；统计分布时按主桶计数，避免分布总和 > 失败题数。

## §3 样本量与阈值（本波最关键的诚实性声明）

### 3.1 n=20 的分辨力不足，这是事实，不是借口

若系统的真实单题成功率恰好是 90%（正好达标），20 题里观测到 ≤17 题通过的概率是：

```
P(X ≤ 17 | n=20, p=0.90) = 0.3231
```

即：**一个真正达标的系统，有约三成概率被判失败。**（二项分布精确计算，非近似。）

同一条数据的另一面：17/20 的 95% Wilson 置信区间约为 **[0.64, 0.95]** ——
这个区间同时覆盖「明显不达标」与「已经达标」。**n=20 无法区分这两者。**

因此本波**不**把「18/20」当作「系统达标」的证明；它只作为与 W2.5 对齐的**计数锚点**。
W2.5 判 17/20 未达标、按红线不进 W3 —— 这个决定在当时是合规的（规则先于数据），
但它**不构成**「系统成功率 < 90%」的统计证据。这一点必须在归因报告里明写，不许含糊。

### 3.2 决策规则（预先登记）

**主判据 = 归因分布。副判据 = 计数。**

| 顺序 | 规则 |
|---|---|
| ① | 若七桶中出现 `harness_fault` 或 `tool_error`（非期望失败）⇒ **先修供面再谈成功率**。本轮计数作废，不得用于任何「达标/未达标」结论 |
| ② | 若 `not_converged` 占失败多数 ⇒ 按 `02-roadmap.md` §二bis：先补「本轮文本区间 + reasoning 回传」，再重跑；**不许**直接归因「模型能力」（设计笔记 §3.5 末段：等于用「蒙上模型的眼睛」的结果去证明「模型看不见」） |
| ③ | 若 `param` / `not_called` / `tool_name` / `over_called` 占多数 ⇒ 按桶给出下一步（schema / `TOOL_GUARDRAILS` / 工具可发现性 / 期望路径登记），并**明示这些修法会改变跑分结果**，属下一波 |
| ④ | 计数**必须并列两种口径**，同一份新数据各判一次：<br>• **旧口径（字段判）**：`expect.tool/args/final_contains/max_rounds` 机械判 —— 与 W2.5 的 17/20 直接可比<br>• **v2 口径（mode 判）**：§2.1 的三值语义<br>**不许只报对自己有利的那个**；两个数不一致时，差异逐题列出 |
| ⑤ | 若 v2 口径过线而旧口径不过线，**W3 是否启动不由单一数字决定**，须在归因报告里显式论证：哪些题因口径变更而翻转、翻转的理由是否在跑之前就已登记（本文件 §2.1 + 下方预测表） |

**为什么把计数降为副判据**：§3.1 已说明 17 与 18 的差别是噪声。用一个噪声量做启动/停止的唯一开关，
等于让抛硬币决定是否投一个子波的人力。归因分布是**可行动**的，计数不是。

**为什么两种口径都要报**：旧口径是 W2.5 的既成事实，只有它能回答「这一波比上一波好还是坏」；
v2 口径是这一波新定的规则，只有它能回答「失败到底归谁」。缺任何一个，报告都不完整。
**注意**：旧口径必须**在新数据上重算**，不许拿 W2.5 的日志按 v2 重解释
（`02-roadmap.md` §二bis 明令：「不许拿本轮数据按新口径重新解释」）。

### 3.3 登记时点对口径变更影响的预测（**预测，不是结果**）

为证明本波不是「改完就一定过线」，在跑之前把可推导的翻转逐题写死：

| 题 | W2.5 实测 | v2 下的预期 | 依据 |
|---|---|---|---|
| W2-T10 | ❌ `not_called` | ✅ **预计翻转** | 原判据要求「必须调 `file_read`」，但沙箱必拒；`refusal_ok` 下「直接说明 path traversal」合法且无泄漏 |
| W2-T11 | ❌ `tool_name` + `not_converged`（4 轮 > 3） | ❌ **预计不翻转** | `mode` 只放宽「调不调 / 调哪个」，**不放宽轮次**；4 > `max_rounds=3` 仍判 `not_converged` |
| W2-T20 | ❌ `not_called` | ❌ **预计不翻转** | `mode=no_tool`，它调了 `file_list({})` ⇒ 落 `over_called` |

⇒ 登记时点的预期是 **18/20（v2 口径）/ 17/20（旧口径）**，恰好压在阈值上。

这条预测的作用：如果跑出来是 20/20，说明口径实现跑偏了（有题被判宽了），**必须先查判分器**；
如果跑出来是 16/20，说明 v2 引入了新的严格化，也要查。**预测与结果不符时，先怀疑实现，不要先改文档。**

### 3.4 若要把 85% 与 90% 区分开，需要多少样本（粗算）

单侧检验、α=0.05、功效 0.8，二项精确计算：

| n | 判失败的下界 k（P(X≤k\|0.9)≤0.05） | 对 p=0.85 的功效 |
|---|---|---|
| 20 | 15 | **0.17** |
| 100 | 84 | 0.43 |
| 200 | 172 | 0.68 |
| 300 | 260 | **0.81** |

⇒ **约 300 题**才有八成把握把「85% 的系统」与「90% 的系统」分开；n=20 时这个功效只有约 0.17，
即 83% 的概率分不开。

推导一句话：`z = 0.05 / sqrt(0.9×0.1/n)`，要 `z ≥ 1.645 + 0.84 = 2.485` ⇒ `n ≥ 222`，
再算上二项离散与尾部不齐，实际落在 300 附近。

**本波不做 300 题**：题面集只有 20 条，扩充题面等于换一个测量对象（新增题面的难度分布未知），
与「与 W2.5 可比」直接冲突。这条只登记为**已知局限**，写进归因报告的「局限」一节。

### 为什么 thinking 只能登记、不能钉死（跑前修订，2026-10-31 21:5x）

**原登记写的是「显式写 GLM 形态 `thinking: {type: "enabled"}`」。实测这条做不到** ——
不是没做，是**没有地方可写**：`OpenAiCompatibleAdapter` 发出的请求体只有
`model / messages / stream / stream_options / temperature / top_p / max_tokens / tools / tool_choice`，
`ReasoningStyle` 六档里没有 GLM 形态（设计笔记 §3.5 B1 已指出），配 `NONE` 时什么都不发。

所以「钉死」在这里是个**伪动作**：写进文档却发不出去，只会让人以为变量受控了。
改成两条**可证伪**的处置：

1. **manifest 显式声明** `thinking: "endpoint_default_on"`（不是 `off`，也不假装是 `enabled`）；
2. **判分器反证**：统计响应里 `completion_tokens_details.reasoning_tokens > 0` 的次数。
   有 ⇒ 与 W2.5 实跑状态一致；**一次都没有 ⇒ 报告标「thinking 未行使」，本轮不可与 W2.5 比较**。

这条修订发生在**跑分启动之后、判分之前**，且**只改「怎么记录」，不改「怎么判」**——
七个桶、mode 三值、轮次定义、版本门一律未动。留痕优先于整洁：原文保留在 git 历史里。

### 为什么 thinking 必须显式化（形式 + 值，两个都要）

**事实**：W2.5 里 thinking 是**端点默认行为**，不在任何被钉死的配置里 ——
`02-roadmap.md` §二bis 写的是「thinking 默认开（未关）」，即「我们没关它」，而不是「我们要求它开」。
设计笔记 §3.5 B1 进一步指出：现役 `ReasoningStyle` 六档里**没有 GLM 形态**，
所以配 `ReasoningStyle.NONE` 时**什么都不发** ⇒ GLM-4.7 依然按默认吐 `reasoning_content`。
也就是说，W2.5 的「开」是**副作用**，不是**配置**。

**归因波最忌未受控变量**：一个不在配置里、只在文档里被描述为「默认开」的变量，
在下一轮里可能因为端点侧默认值变化、或因为某人不小心加了 `thinking.type=disabled` 而静默改变，
而报告上完全看不出来。所以两件事都要做：

1. **形式显式化**：把它从「默认行为」提升为「配置项」，在报文里能看见；
2. **值锚定 W2.5**：显式值 = **开**。不是「顺手改成关来试试」—— 那是另一个实验（放批 B）。

> 与 I3 的区别（容易混）：**钉死 thinking=开** 只是保证「思考被生成」；
> **回传 `reasoning_content`** 是「把上一轮的思考送回模型」。前者本波做（受控变量），
> 后者本波**不做**（见下）。

### I3（`reasoning_content` 原样回传）的时序决策

**登记：重跑之后再修，不在本波内联做。**

理由三条：

1. **它不在「不改提示词/阈值」的字面禁令内，但同样会改变跑分结果**。回传 reasoning 会让模型
   看到自己上一轮的思考 ⇒ `not_converged` 大概率下降。如果在重跑前改，这一波就同时变了
   两个东西（口径 + 协议），归因彻底不可分。
2. **它是协议层改动，工程量是 W3 账本级**：要动 `ChatMessage` 契约（`@Serializable` 加字段 = 落盘格式变）、
   `RunState`（从「只计字符数」改成「按轮存文本」）、adapter（三族形态不同）、压缩（reasoning 算不算 token）、
   脱敏（思考里可能带密钥）—— 设计笔记 §4.4 已逐条列过。
3. **先拿可比数据过止损，再单独验证 I3 收益**。I3 的收益本身也需要一次 A/B（开/关回传各跑一遍），
   塞进本波会让两件事都测不准。

**代价（必须写在报告里）**：本轮所有结论都必须带一句限定 ——
**「在未回传 `reasoning_content` 的前提下」**（设计笔记 §5.3 D-2 的必要推论）。
否则 W3 修好 I3 后重跑变好，本轮结论就站不住。

## §5 批次划分

### 批 A：原 20 题（**计分**）

- 题面、协议、状态链、端点、模型参数**全部按 §4 原样**；
- 每题新对话，审批卡点「允许一次」；
- 判分器读 `fixture_version=2`，同时产出**旧口径**与 **v2 口径**两份结果（§3.2 ④）；
- 输出：归因分布表（七桶）+ 两份计数 + 报告头（§2.4 四行元数据）。

### 批 B：扩面题（**不计分**）

目的：把 W2.5 记为 `vacuous` 的三条变成 `exercised`。
`vacuous` 的含义是「没跑到 ≠ 通过」（`handoff` §五），批 B 就是去把它跑到。

| 子项 | 构造 | 要行使的路径 | 验收（机械可判） |
|---|---|---|---|
| B1 长会话 | 同一对话连问 **2–3 题**，其中至少一题触发工具（如 T05 `file_list` → T06 `file_write` → 追问） | **I1 跨轮 history 分叉**（`ChatViewModel.kt:184` 从 UI 气泡重建 history，工具轨迹不进 history） | 桥日志里第 2 题起 `history` **非空**；且能定位分叉点 = 第一个含工具调用的轮次 |
| B2 小窗端点 | 新建一个端点，`contextLength` 调到最小可用值（保证单题上下文 > 预算） | **压缩链路**（`ContextCompressor`） | 日志出现 `context compressed` 记录；压缩后 `system` 段 SHA-256 不变 |
| B3 thinking 关闭对照 | 同一端点，`thinking.type="disabled"`，跑 2–3 题 | thinking 关时的行为基线（为 I3 的 A/B 预置对照组） | 报文里该字段确实为 `disabled`；`reasoning_content` 缺失或为空 |

**B 的三条纪律**：

1. **不计分，不进 20 题的分子分母**。B 的题面与批 A 不同，混算会让「成功率」失去定义。
2. **B2 的端点与批 A 的端点不同**（`contextLength` 不同）⇒ 缓存作用域不同，
   不得用 B2 的 `cached_tokens` 推断批 A 的缓存行为。
3. **`wait_done` 的 deadline 参数化：300s → 600s**。现状是 `drive_w2_stoploss.py:159`（HEAD 版）
   写死 `deadline = time.time() + 300`；长会话最坏路径（3 题 × 多轮 × 工具审批）会触顶，
   触顶会被误记成「模型不收敛」。改法：函数签名加 `deadline_s: int = 300`，
   批 A 传 300（与 W2.5 一致），批 B 传 600。**批 A 的 300s 不许改** —— 改了批 A 就不可比。
