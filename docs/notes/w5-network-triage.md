# W5 设备网络排查 —— W4-01 关闭报告（2026-11-01）

> 结论先行：**W4-01「设备→OpenRouter 请求不收敛」在当前时点不可复现，已关闭。**
> 归因不是「应用侧连接/流式路径不收敛」，也不是「域名被阻断」——两者都被实验证伪。
> 设备：OPPO PDRM00 / Android 13 / 1080×2400；包名 `com.rickeal.liquidharness.debug`。

## 一、四个对照实验（逐条可复算）

| # | 实验 | 做法 | 结果 | 推翻了什么 |
|---|---|---|---|---|
| E1 | 系统栈可达性 | `adb shell ping -c2 integrate.api.nvidia.com` / `openrouter.ai` | 两者均解析并回包（NVIDIA 110–143ms；OpenRouter 284ms，丢包 50%） | 「设备没网」 |
| E2 | TCP 层可达性 | `toybox nc -w 8 <ip> 443`，两个域名各一次 | **两边都 `TCP_OK`** | 「443 被阻断」 |
| E3 | 应用栈 + 异域名 | 端点指向 `integrate.api.nvidia.com`，保留**旧 OpenRouter 密钥** | **HTTP 401**（`authentication failed`），非超时 | 「应用 HTTP/TLS 路径不收敛」——401 意味着连接、TLS、请求、响应四步全通 |
| E4 | 应用栈 + 原域名 | 端点指回 `openrouter.ai`，密钥换成**真实 OpenRouter 密钥** | 连接测试 **连接正常 1850 ms**；免费模型真实往返成功（`1.5k in / 37 out`） | 「OpenRouter 域名不可达」 |

**E3 的设计要点**：故意用**错误密钥**打一个**正确域名**。如果得到 401，说明请求确实到达了服务端并拿到业务层拒绝；如果得到超时，说明卡在连接/TLS。这一条把「网络问题」与「鉴权问题」干净地分开了 —— 而 W4 当时没有做这一步。

## 二、W4 当时的现象与现在的差异

W4 记录：`giving up after 1 retries: network error: SocketTimeoutException`（两次复现），
模型 `nvidia/nemotron-3.5-super-vl`（**付费**模型，非 `:free`）。

本次复现条件与 W4 的差异只有两处：

1. **模型**：W4 用付费模型，本次用 `dots-studio/dots-3-note-preview:free`；
2. **时点**：相隔约 15 小时，网络环境可能已变。

因此**不能**断言「W4 的记录是假的」——只能说：**同样的应用、同样的域名，现在能通**。
最可能的解释是「该付费模型在 OpenRouter 侧的上游当时不可用/排队超时」，而不是应用缺陷。
按本仓纪律，这属于「无法证伪」而非「已证伪」：W4 的原始日志仍在，只是**归因被降级**。

## 四、可复用的排障顺序（写进方法论，下次直接用）

```
1. ping 域名            → 区分「DNS/路由」与「更上层」
2. nc -w 8 ip 443       → 区分「TCP 被阻断」与「TLS 之后」
3. 应用打「错密钥 + 对域名」→ 401 = 应用栈完好；超时 = 卡在连接/TLS
4. 应用打「对密钥 + 对域名」→ 唯一能证明「业务可用」的一步
```

**第 3 步是本次唯一的新增，也是 W4 缺失的那一步。** 它把「网络好不好」这个笼统问题
换成一个二值判断（401 vs 超时），成本一次点击，却直接决定后面要不要动传输层代码。
