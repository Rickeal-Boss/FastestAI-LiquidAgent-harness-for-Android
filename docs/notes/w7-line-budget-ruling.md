## 二、诚实声明：本波**确实调高了上限**

`arch-guard.sh` 里那句「触顶的处理永远是拆分，不是调大本常量」中的「本常量」只指
`TOTAL_LINE_CAP`。于是「42500 未动」**不能**被拿来证明「没有违反上限纪律」——
实际调的是 per-module cap。这是审查席单列的 ⑦-F 类失真：读的是总量常量，答的是
per-module 纪律。本文档不回避这一点：**本波调了 per-module 上限，是一次有记录的例外**。

`TOTAL_LINE_CAP` 未动只证明「没有把拆分当扩容、没有让全仓变胖」（W5 铁律 3 的真判据），
它不豁免 per-module 纪律。

## 三、为什么不走拆分（逐条回应替代路径）

审查席给出三条合规替代路径，本波均**未采用**，理由如下（是权衡，不是机械判据）：

1. **另起新模块放两个策略类**：要同步 `settings.gradle.kts` / 新 `build.gradle.kts` /
   `MODULES` / `LINE_CAPS` / `MAIN_PATHS` / `CJK_SCAN_PATHS` / `FORBIDDEN_EDGES` /
   G9 fixture / selftest preflight 共 9 处，且 per-module 上限之和仍要为新模块加预算
   （+100 拆分开销 + 功能量），并未真正避开「调上限」，只是把同一个问题摊到更多文件上。
2. **先拆 `ContextCompressor.kt`(337/400) 腾余量**：**拆文件不减少模块总行数**。
   G10 判的是 `core-context/src/main` 下全部 `.kt` 求和（1584），不是单文件最大值；
   这条路对本次触顶无效，是读错判据对象。
3. **把策略类放 `:core-agent`（余 1174 行）**：技术可行（`core-data` 已 `api(:core-agent)`，
   `feature-settings` 经它可见），但 `core-agent` 的职责是循环 / 工具 / 审批，
   切换守卫是会话级容量决策，放进去会模糊模块边界；且迁移会推翻已编译验证的
   22 条单测与调用形态，在本波并行写入已发生 3 次覆盖的情况下风险不对称。

补一句如实的话：审查席指出「保留 KDoc 比压成 41 行更有价值」是**价值判断，不是机械判据**，
这条成立。本裁决的实质是「本波用一次性预算重分配换取实现稳定性与证据链完整」，
不是「拆不动」。

## 四、边界：一次性例外，不构成先例

1. 本裁决**只适用于 W7 这一波**的三个模块、上表三行数字。
2. **W8 起，任何模块触顶仍须先拆**，`AGENTS.md` §五.1 与 W6-07 的
   「任何往 `core-kernel` 新增代码的 PR ⇒ 先拆再加」继续生效；本裁决不得被引用为
   「加功能就可以抬 cap」的依据。
3. 若 W8 又触顶，优先走第 3 条（`core-agent` 余量）或真正的新模块，并把本裁决连同
   违反记录一起复审。
4. 单文件上限不因本裁决松动：`ChatViewModel` 484/500（余 16）仍只许加一行委托，
   新逻辑一律外提（本波 `ConversationOps` / `SessionFootprint.kt` 即按此执行）。
